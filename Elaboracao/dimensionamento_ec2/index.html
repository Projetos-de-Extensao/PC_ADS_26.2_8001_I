    1. INTRODUÇÃO¶

    1.1. Propósito¶

    Este documento apresenta o Modelo de Análise (Classes de Análise) para o dimensionamento da camada de computação Amazon EC2 do Portal Cidadão Seguro na AWS. O documento descreve as classes de análise que representam a execução da API, o escalonamento horizontal, a distribuição de tráfego, o registro de instâncias, os templates de lançamento e as políticas de escala.

    O dimensionamento utiliza as premissas de carga já estabelecidas para o Portal, mas distingue valores de referência, hipóteses de projeto e configurações propostas. As capacidades finais deverão ser validadas com teste de carga, pois ainda não há benchmark real da API em produção.

    O modelo é derivado dos seguintes artefatos:

    • Documento de Visão — Portal Cidadão Seguro;
    • Documento de Requisitos Suplementares — Portal Cidadão Seguro;
    • Casos de Uso Arquiteturais — Portal Cidadão Seguro;
    • Modelo de Análise (Pacotes/Subsistemas) — Portal Cidadão Seguro;
    • Modelo de Análise (Classes) — Dimensionamento de RDS — Portal Cidadão Seguro.

    1.2. Escopo¶

    O documento abrange a camada de computação da API da plataforma, considerando:

    • Instância de computação (ComputeInstance) para executar a API Django REST Framework;
    • Auto Scaling Group (AutoScalingGroup) para administrar a quantidade de instâncias EC2;
    • Application Load Balancer (LoadBalancer) para distribuir o tráfego;
    • Target Group (TargetGroup) para registrar e verificar a saúde das instâncias;
    • Launch Template (LaunchTemplate) para padronizar as instâncias;
    • Políticas de escalonamento (ScalingPolicy) para reagir a aumentos de utilização;
    • cálculo preliminar de CPU, memória, número de instâncias e armazenamento EBS;
    • estimativa inicial de custos e comparação de alternativas;
    • mecanismos de monitoramento, implantação e recuperação da camada de aplicação.

    O cenário de projeto é um único município do Estado do Rio de Janeiro. O Portal é a plataforma comum; a Zeladoria Urbana é o primeiro serviço considerado, sem impedir a inclusão de outros serviços futuramente.

    Fora do escopo: dimensionamento do RDS (documento separado), dimensionamento do S3, NAT Gateway, camada de rede detalhada, ECS/Fargate, CI/CD definitivo e dimensionamento para todos os municípios do Estado.

    1.3. Definições e siglas¶

    Sigla Definição
    EC2 Amazon Elastic Compute Cloud — máquinas virtuais na AWS.
    ALB Application Load Balancer — balanceador de carga na camada HTTP/HTTPS.
    ASG Auto Scaling Group — grupo que mantém e ajusta a quantidade de instâncias EC2.
    AMI Amazon Machine Image — imagem usada para criar instâncias.
    EBS Elastic Block Store — armazenamento em bloco anexado às instâncias.
    TPS / RPS Transações ou requisições processadas por segundo. Neste documento, o valor representa operações HTTP/API estimadas, não uma medição real.
    AZ Availability Zone — zona de disponibilidade da AWS.
    SG Security Group — conjunto de regras de tráfego de rede.
    SSM AWS Systems Manager — gerenciamento e acesso administrativo às instâncias.
    RPO Recovery Point Objective — perda máxima de dados aceitável.
    RTO Recovery Time Objective — tempo máximo desejado para recuperação.
    PITR Point-in-Time Recovery — recuperação do banco para um ponto no tempo.
    LGPD Lei Geral de Proteção de Dados.

    2. VISÃO GERAL DO DIMENSIONAMENTO¶

    2.1. Requisitos e premissas que impactam o dimensionamento¶

    Requisito / premissa Valor adotado Fonte / observação
    Escopo geográfico 1 município Limite definido para o projeto.
    Usuários de referência Até 1.000.000 Capacidade de projeto baseada na referência de alcance/usuários discutida para o portal; não significa que todos estarão ativos simultaneamente.
    Acessos diários ao Portal 52.000/dia Valor de referência adotado no dimensionamento anterior.
    Média de acessos 0,60/s 52.000 / 86.400. É média diária, não tráfego uniforme.

    Fator de pico 10× Margem de projeto para representar períodos de maior demanda.
    Carga de pico modelada Aproximadamente 10 RPS 0,96 × 10 = 9,6 RPS, arredondado. Precisa ser validado por teste.

    Instâncias máximas do ASG 4 Margem de expansão inicial; não é garantia de suportar qualquer pico sem teste.
    Meta numérica de latência Não definida nos requisitos Definir SLO de API e validar com teste de carga. Não se copia o limite de 200 ms do SwiftTrack.
    SLA numérico de aplicação Não definido formalmente A arquitetura procura reduzir pontos únicos de falha; não se afirma um SLA contratual.
    RPO / RTO ≤ 15 min / ≤ 1 h Metas da plataforma; RPO depende principalmente do RDS/backup e RTO deve ser validado de ponta a ponta.
    Região de referência US East (N. Virginia), us-east-1 Mantida consistente com o dimensionamento RDS anterior.
    Orçamento total do projeto Não definido neste documento Não herdar o orçamento do SwiftTrack.
    Orçamento alocado para EC2 A definir Comparar com a AWS Pricing Calculator e o orçamento do projeto.

    Observação importante sobre a carga¶

    Os 52.000 valores diários representam acessos/sessões usados como referência. Não equivalem automaticamente a requisições HTTP nem a operações SQL. Para permitir o cálculo acadêmico, este documento adota uma aproximação: uma chamada comum para consultar o catálogo do Portal por acesso e três chamadas adicionais por acesso à Zeladoria. Esse modelo precisa ser substituído por métricas reais ou refinado quando os endpoints da aplicação estiverem definidos.

    2.2. Arquitetura de computação proposta¶

    A proposta utiliza um único Application Load Balancer regional associado a duas sub-redes públicas, com as instâncias EC2 em sub-redes privadas distribuídas por duas Availability Zones. O Auto Scaling Group mantém duas instâncias como capacidade base e pode crescer até quatro.

    Fluxo de rede¶

    • O ALB é o ponto de entrada público, escutando HTTPS na porta 443; HTTP na porta 80 deve redirecionar para HTTPS.
    • O ALB encaminha tráfego HTTP pela VPC para a porta 80 do Nginx nas instâncias EC2.
    • O Nginx encaminha as solicitações para Gunicorn/Django localmente, por exemplo na porta 8000.
    • O Security Group das instâncias permite entrada na porta 80 somente a partir do Security Group do ALB.
    • As instâncias não recebem IP público e não aceitam SSH aberto à Internet. O acesso administrativo deve preferir AWS Systems Manager Session Manager.
    • A API acessa o RDS pela porta 5432 por regra restrita entre Security Groups; acesso a imagens ocorre pelo S3 conforme o papel IAM da aplicação.
    • A saída das sub-redes privadas para atualizações ou serviços externos depende da solução de rede/egress do projeto, tratada no documento de rede, e não está incluída no custo desta camada.

    3. ESPECIFICAÇÃO DAS CLASSES DE ANÁLISE¶

    3.1. CLASSE: COMPUTEINSTANCE¶

    3.1.1. Responsabilidade¶

    Representar uma instância EC2 que executa a API do Portal Cidadão Seguro, incluindo Django REST Framework, Gunicorn e Nginx. A instância fornece a capacidade computacional para atender às requisições encaminhadas pelo ALB.

    3.1.2. Atributos¶

    Atributo Tipo Valor proposto Justificativa
    instanceType String t3.medium 2 vCPU e 4 GiB de memória; memória adicional em relação a t3.small favorece a execução de processos Python. A capacidade final será validada por teste.
    ami String Amazon Linux 2023, x86_64 AMI Linux da AWS com suporte ao Systems Manager Agent; o ID da AMI será resolvido na região durante a implantação.
    vpcId String VPC do Portal Mantém a instância dentro da rede isolada definida pelo projeto.
    subnetId String Private Subnet A ou B Evita exposição direta da instância à Internet.
    securityGroup SecurityGroup SG-EC2-API Permite entrada HTTP somente do SG do ALB e saída restrita aos destinos necessários.
    iamRole String Portal-EC2-Role Permissões mínimas para CloudWatch, Systems Manager e acesso à aplicação aos serviços AWS necessários, como S3.
    ebsVolume String 20 GiB gp3 Volume raiz para o sistema operacional, dependências e artefato da aplicação; arquivos enviados pelos usuários ficam no S3.
    userData String Bootstrap de inicialização Configura ambiente e inicia a aplicação; segredos não devem ser gravados no script.
    privateIp String Dinâmico na sub-rede O IP é atribuído dentro da VPC e não deve ser fixado no documento.
    publicIp Boolean false O acesso público passa pelo ALB.
    monitoring Boolean true Usa métricas e registros de monitoramento; CloudWatch Agent pode ser configurado para métricas do sistema operacional.
    ebsOptimized Boolean true Mantém a configuração de EBS otimizada, de acordo com o suporte do tipo escolhido.
    detailedMonitoring Boolean false inicialmente O monitoramento básico é o ponto de partida; monitoramento detalhado pode ser ativado se a frequência de um minuto for necessária.

    3.1.3. Responsabilidades (métodos)¶

    Responsabilidade Descrição Retorno
    start() Inicia a instância. void
    stop() Para a instância, quando apropriado fora da operação gerenciada pelo ASG. void
    terminate() Encerra a instância; normalmente a operação é gerenciada pelo ASG. void
    getMetrics() Obtém métricas de CPU, rede, estado e métricas adicionais instaladas. Metrics
    applyUserData() Executa o bootstrap definido no Launch Template. void
    attachToTargetGroup(group) Registra a instância no Target Group, via integração do ASG. void
    getPrivateIp() Retorna o endereço privado da instância. String

    3.1.4. Relacionamentos¶

    Relacionamento Multiplicidade Descrição
    AutoScalingGroup → ComputeInstance 1 : 2..4 O grupo mantém duas instâncias como base e pode escalar até quatro.
    LaunchTemplate → ComputeInstance 1 : 0..* O template fornece a configuração para cada nova instância.
    SecurityGroup → ComputeInstance 1 : 1..* O SG restringe o tráfego de rede das instâncias.
    TargetGroup → ComputeInstance 1 : 2..4 O Target Group registra instâncias saudáveis para receber tráfego.

    3.1.5. Justificativa do dimensionamento¶

    Os números abaixo são hipóteses de cálculo, não resultados de benchmark da API.

    Componente Cálculo Resultado
    Operações de API no pico 83.200/dia ÷ 86.400 × fator 10 ~9,6 RPS, arredondado para 10 RPS
    CPU estimada por requisição Premissa para cálculo 5 ms
    CPU bruta no pico 9,6 requisições/s × 0,005 s CPU 0,048 vCPU equivalente
    CPU com fator de segurança 4× 0,048 × 4 0,192, aproximadamente 0,2 vCPU equivalente
    Memória por worker Premissa de planejamento 150 MiB
    Workers por instância Configuração inicial proposta 4
    Memória dos workers por instância 4 × 150 MiB ~600 MiB
    SO, Nginx e agentes Estimativa de planejamento ~1,4 GiB
    Cache, overhead e reserva operacional Estimativa de planejamento ~1,0 GiB
    Memória total estimada por instância 0,6 + 1,4 + 1,0 GiB, aproximadamente ~3,0 GiB
    Instância proposta 2 vCPU e 4 GiB t3.medium
    Carga de pico por instância com 2 instâncias saudáveis 9,6 ÷ 2 ~4,8 RPS por instância, apenas como distribuição estimada
    Instâncias base Requisito de redundância entre AZs 2
    Instâncias em pico Capacidade máxima inicial configurada no ASG 4; a capacidade real deve ser verificada em teste

    A quantidade de vCPU calculada é pequena; a escolha de t3.medium considera também a memória de processo, a margem operacional e a necessidade de manter uma instância restante apta a atender a API se a outra ficar indisponível. Não se afirma que t3.medium suporta um RPS máximo específico sem benchmark.

    3.1.6. Estimativa de custo¶

    A estimativa preliminar usa preços públicos de referência para us-east-1, Linux/Unix On-Demand, 730 horas mensais e dois volumes gp3 de 20 GiB. O valor final deverá ser conferido na AWS Pricing Calculator.

    Componente Configuração Custo mensal estimado
    EC2 2 × t3.medium × US$ 0,0418/h × 730 h US$ 61,03
    EBS 2 × 20 GiB gp3 × US$ 0,08/GiB-mês US$ 3,20
    ALB — tarifa horária 1 × US$ 0,0225/h × 730 h US$ 16,43
    ALB — LCU Hipótese de 1 LCU média × US$ 0,008/h × 730 h US$ 5,84
    IPv4 público do ALB Hipótese mínima de 2 endereços × US$ 0,005/h × 730 h US$ 7,30
    Subtotal preliminar da camada de computação 2 EC2 + volumes + ALB e hipóteses de LCU/IPv4 US$ 93,80/mês

    O valor acima não é uma cotação final da calculadora. Não inclui transferência de dados para a Internet, ingestão/armazenamento de logs, custo de NAT Gateway/egress da rede, créditos de CPU adicionais de instâncias T3 caso ocorram, impostos ou custos de outros serviços. O LCU e a quantidade de IPv4 devem ser confirmados na calculadora. Auto Scaling, Launch Template, Target Group e políticas de escala não possuem uma tarifa direta própria; os recursos consumidos e CloudWatch podem ser cobrados. A AWS informa que o preço On-Demand é cobrado pelo tempo da instância e que o Auto Scaling não cobra uma taxa adicional pelo grupo em si.

    3.2. CLASSE: AUTOSCALINGGROUP¶

    3.2.1. Responsabilidade¶

    Manter a quantidade desejada de instâncias EC2, substituir instâncias não saudáveis e permitir escala horizontal quando a demanda ou a utilização dos recursos aumentar.

    3.2.2. Atributos¶

    Atributo Tipo Valor proposto Justificativa
    name String pcs-asg-api Nome do grupo de computação do Portal.
    minSize Integer 2 Mantém capacidade em duas AZs.
    maxSize Integer 4 Permite adicionar até duas instâncias além da base, mantendo o custo limitado na primeira versão.
    desiredCapacity Integer 2 Capacidade inicial, uma instância por AZ.
    healthCheckType String ELB Considera o estado reportado pelo Target Group/ALB.
    healthCheckGracePeriod Integer 300 segundos Dá tempo para a aplicação iniciar antes de tratar a instância como não saudável.
    defaultCooldown Integer 300 segundos Reduz oscilações durante alterações de capacidade.
    availabilityZones List Duas AZs em us-east-1 Distribuição entre zonas.
    launchTemplate LaunchTemplate pcs-lt-api Define tipo de instância, AMI, volume, SG e IAM role.
    targetGroupArns List Target Group da API Registra instâncias no ALB.
    scalingPolicies List Scale-out e scale-in Ajusta a capacidade de acordo com CPU média.
    terminationPolicies List Política padrão do ASG Seleção gerenciada da instância a remover durante scale-in.

    3.2.3. Responsabilidades (métodos)¶

    Responsabilidade Descrição Retorno
    scaleOut() Aumenta o número de instâncias até maxSize. void
    scaleIn() Diminui o número de instâncias sem ultrapassar minSize. void
    updateDesiredCapacity(capacity) Atualiza a capacidade desejada. void
    getInstances() Retorna as instâncias registradas no grupo. List<ComputeInstance>
    attachToTargetGroup(group) Integra o grupo com o Target Group. void
    applyScalingPolicy(policy) Associa uma política de escalonamento. void
    getHealthStatus() Retorna a condição das instâncias. HealthStatus

    3.2.4. Relacionamentos¶

    Relacionamento Multiplicidade Descrição
    AutoScalingGroup → ComputeInstance 1 : 2..4 Mantém entre duas e quatro instâncias.
    AutoScalingGroup → LaunchTemplate 1 : 1 Usa um template versionado.
    AutoScalingGroup → ScalingPolicy 1 : 2 Associa política de expansão e de redução.
    AutoScalingGroup → TargetGroup 1 : 1 Registra as instâncias no Target Group da API.

    3.2.5. Justificativa do dimensionamento¶

    Componente Cálculo / critério Resultado
    Capacidade base Uma instância por AZ 2 instâncias
    Capacidade desejada inicial Carga estimada baixa e requisito de redundância 2 instâncias
    Capacidade máxima inicial Margem de crescimento para a primeira versão 4 instâncias
    Carga de pico estimada Workload lógico com fator 10× ~10 RPS no total
    Capacidade por instância Não medida; carga distribuída teoricamente por instância ~4,8 RPS com 2 instâncias saudáveis
    Scale-out CPU média > 70% em 2 períodos de 5 minutos Adicionar 1 instância
    Scale-in CPU média < 30% em 3 períodos de 5 minutos Remover 1 instância, respeitando mínimo 2
    Tempo de inicialização Estimativa operacional Validar no ambiente; grace period inicial de 300 s

    O limite máximo de quatro instâncias é uma decisão inicial de contenção de custo e expansão gradual, não uma garantia matemática de suportar uma carga 10 vezes maior. O número máximo deverá ser revisto após testes de estresse e observação das métricas.

    3.2.6. Estimativa de custo¶

    O AWS Auto Scaling não tem tarifa adicional para o grupo em si. O custo cresce quando ele inicia mais instâncias, volumes EBS e métricas/alertas associados.

    Componente Configuração Custo mensal estimado
    Capacidade base 2 × t3.medium Incluída no subtotal EC2: US$ 61,03
    Instâncias adicionais Até 2 instâncias adicionais em períodos de pico Variável conforme horas utilizadas
    Política de escala / ASG Recurso de gerenciamento US$ 0,00 de tarifa direta; CloudWatch pode gerar cobrança

    Como ilustração, duas instâncias extras executadas durante 10% de um mês de 730 horas acrescentariam cerca de US$ 6,10 em computação, antes de EBS, IPv4, métricas, tráfego e outros custos aplicáveis.

    3.3. CLASSE: LOADBALANCER¶

    3.3.1. Responsabilidade¶

    Distribuir o tráfego HTTP/HTTPS de entrada entre instâncias saudáveis da API, fornecer um ponto de entrada estável e terminar TLS no listener HTTPS.

    3.3.2. Atributos¶

    Atributo Tipo Valor proposto Justificativa
    name String pcs-alb-api Nome do balanceador.
    type String Application Adequado a tráfego HTTP/HTTPS e roteamento na camada de aplicação.
    scheme String internet-facing O portal é acessado publicamente.
    securityGroup SecurityGroup SG-ALB Permite HTTPS e redirecionamento de HTTP para HTTPS.
    subnets List Duas sub-redes públicas em AZs distintas O ALB precisa estar associado a sub-redes de mais de uma AZ para a arquitetura proposta.
    listeners List 80 → redirect 443; 443 → Target Group HTTP:80 Redireciona tráfego não criptografado para HTTPS.
    certificate String Certificado público ACM O domínio definitivo deve ser configurado antes da emissão do certificado.
    idleTimeout Integer 60 s Valor inicial, revisável conforme comportamento da API.
    deletionProtection Boolean true Evita exclusão acidental do recurso.
    accessLogs Boolean true como proposta Logs de acesso podem ajudar na análise operacional; bucket, retenção e proteção devem ser definidos.
    dnsName String Atribuído pela AWS O DNS final será o endpoint do ALB ou domínio configurado posteriormente.

    3.3.3. Responsabilidades (métodos)¶

    Responsabilidade Descrição Retorno
    addListener(listener) Adiciona listener. void
    removeListener(listener) Remove listener. void
    getDnsName() Retorna o DNS do ALB. String
    healthCheck() Consulta saúde dos destinos por meio do Target Group. HealthStatus
    terminateSsl() Gerencia a terminação TLS no listener HTTPS. void

    8. MEMÓRIA DE CÁLCULO¶

    8.1. Cálculo de carga de API¶

    Carga média do Portal¶

    Segundos por dia = 24 × 60 × 60 = 86.400
Acessos médios/s = 52.000 / 86.400 ≈ 0,60

    Acessos à Zeladoria¶

    52.000 × 20% = 10.400 acessos/dia

    Operações modeladas¶

    Consulta comum ao catálogo:
52.000 acessos/dia × 1 chamada = 52.000 operações/dia

Chamadas adicionais da Zeladoria:
10.400 acessos/dia × 3 chamadas = 31.200 operações/dia

Total:
52.000 + 31.200 = 83.200 operações/dia

    Média e pico¶

    Média = 83.200 / 86.400 ≈ 0,96 operação/s
Pico de projeto = 0,96 × 10 ≈ 9,6 operações/s
Valor arredondado para a memória = 10 RPS

    O fator de pico de 10× é uma premissa de planejamento, não uma medição de distribuição horária dos acessos.

    8.2. Cálculo preliminar de CPU e memória¶

    CPU¶

    Pico de projeto = 9,6 requisições/s
CPU por requisição = 5 ms = 0,005 s (hipótese)
CPU bruta = 9,6 × 0,005 = 0,048 segundos de CPU por segundo
CPU equivalente = ~0,048 vCPU
Margem de segurança = 4×
CPU de planejamento = 0,048 × 4 = 0,192 ≈ 0,2 vCPU

    A conta serve como aproximação para a entrega acadêmica. O tempo de CPU de cada requisição não foi medido; o valor real depende de serialização, autenticação, consultas, lógica de negócio, concorrência e bibliotecas.

    Memória¶

    Componente Hipótese por instância
    Sistema operacional e agentes ~0,8 GiB
    Nginx e sobrecarga fixa da aplicação ~0,6 GiB
    4 workers Gunicorn × 150 MiB ~0,6 GiB
    Reserva para cache, overhead e variação ~1,0 GiB
    Memória de planejamento ~3,0 GiB
    Memória da t3.medium 4 GiB

    A memória por worker é estimada e deve ser conferida com métricas de RSS após executar a aplicação. A memória não cresce de forma linear com cada requisição HTTP; processos e workers mantêm estruturas compartilhadas/individuais.

    8.3. Cálculo do número de instâncias¶

    Métrica Fórmula / critério Resultado
    Instâncias base Uma em cada AZ 2
    Carga de pico modelada 9,6 RPS no total ~10 RPS
    Carga distribuída estimada 9,6 / 2 ~4,8 RPS por instância
    Instâncias desejadas Capacidade inicial + redundância 2
    Instâncias máximas Limite inicial do projeto 4

    A carga por instância representa somente a distribuição esperada do workload. Não representa o limite máximo medido de uma instância. A capacidade efetiva deve ser determinada com teste de carga, observando latência, erros, CPU, memória, conexões com o RDS e créditos de CPU das instâncias T3.

    Esgotamento de conexões do RDS Média Alto Respeitar o max_connections = 100 do modelo RDS e dimensionar pools da aplicação em conjunto.
    Instância T3 consome créditos de CPU além do esperado Baixa/Média Médio Monitorar CPU/CPU credits e reavaliar família/tamanho se houver uso contínuo elevado.
    Custo acima do previsto Média Médio Validar AWS Pricing Calculator, configurar AWS Budgets e monitorar transferências/logs.
    Endpoint de health check inexistente ou dependente de serviço externo Média Médio Implementar /health/ e garantir retorno estável sem incluir dependências frágeis desnecessárias.
    Segredos em User Data ou imagem Baixa Crítico Não colocar segredos em User Data; usar IAM Role e um serviço apropriado de segredos/parâmetros.
    Acesso administrativo indevido Baixa Crítico Não liberar SSH público; preferir Systems Manager e permissões IAM mínimas.

    11. CONSIDERAÇÕES FINAIS¶

    O dimensionamento inicial da camada de computação foi elaborado para um cenário de um município, com aproximadamente 52.000 acessos diários ao Portal e uso inicial de 20% desses acessos pela Zeladoria Urbana. A aproximação de workload — uma chamada comum do catálogo do Portal e três chamadas adicionais por acesso à Zeladoria — resulta em cerca de 83.200 operações modeladas por dia, equivalentes a aproximadamente 0,96 operação por segundo em média e 9,6 operações por segundo no pico estimado com fator de 10×.

    A capacidade proposta usa duas instâncias EC2 t3.medium em sub-redes privadas de duas Availability Zones, um ALB público, Target Group com health check, Launch Template e ASG com capacidade entre duas e quatro instâncias. Essa configuração prioriza redundância básica e uma via de expansão sem afirmar uma capacidade máxima que ainda não foi comprovada por teste.

    A memória de cálculo de CPU e RAM usa premissas explícitas de 5 ms de CPU por requisição e 150 MiB por worker. Essas hipóteses devem ser validadas por teste de carga antes de uma implantação de produção. A escolha de instância e as políticas de escalonamento poderão ser ajustadas a partir de métricas reais.

    A estimativa pública preliminar da camada de computação é de aproximadamente US$ 93,80/mês, incluindo duas instâncias, EBS e uma hipótese inicial de custo do ALB/LCU/IPv4. O valor oficial da entrega deve ser atualizado com a AWS Pricing Calculator e evidenciado por print ou exportação. O custo do RDS permanece separado.

    Os itens abaixo correspondem aos elementos esperados no modelo de referência para o dimensionamento EC2.

    15. FONTES DE PREÇO E DOCUMENTAÇÃO AWS¶

    Preços públicos e capacidades consultados em 21/10/2026. A estimativa é indicativa e deve ser conferida na calculadora antes da entrega final.

    1. EC2 T3 — especificações e tarifa On-Demand: https://aws.amazon.com/ec2/instance-types/t3/ — apresenta, para us-east-1, t3.medium com 2 vCPU, 4 GiB e preço publicado de referência de US$ 0,0418/h para Linux/Unix.
    2. EBS gp3: https://aws.amazon.com/ebs/pricing/ — exemplo de preço de referência de US$ 0,08 por GiB-mês e baseline de 3.000 IOPS / 125 MB/s em regiões com essa tarifa.
    3. Application Load Balancer: https://aws.amazon.com/elasticloadbalancing/pricing/ — tarifa horária e cobrança por LCU; a utilização final depende de conexões, bytes processados e avaliações de regras.
    4. AWS Auto Scaling: https://aws.amazon.com/autoscaling/pricing/ — não há tarifa adicional pelo Auto Scaling Group em si; instâncias e monitoramento são cobrados de acordo com os recursos utilizados.
    5. IPv4 público: https://aws.amazon.com/vpc/pricing/ — a AWS publica cobrança horária para IPv4 público em uso; a quantidade efetiva associada ao ALB precisa ser conferida na configuração.
    6. AWS Pricing Calculator: https://calculator.aws/ — ferramenta recomendada para a estimativa final da arquitetura.
    7. SSM Agent em AMIs: https://docs.aws.amazon.com/systems-manager/latest/userguide/ami-preinstalled-agent.html — lista Amazon Linux 2023 entre as AMIs que normalmente incluem o agente pré-instalado.
